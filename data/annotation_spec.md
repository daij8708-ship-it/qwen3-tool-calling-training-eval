# 数据标注规范 v0（判定规则）

适用范围：六个工具（`search_documents`、`get_record`、`calculate`、`aggregate_data`、`check_availability`、`create_event`）与统一决策格式（`tools/decision_schema.json`）。本规范定义标注员如何给出唯一正确的动作，以及评分器可以依赖的归一化口径。

## 1. 判定顺序

按 ① → ⑤ 顺序判定，命中即停：

| 步骤 | 问题 | 不满足时 |
|---|---|---|
| ① 能力 | 需求能否由 `available_tools` 中某个工具按其 `description` 与枚举取值完成？ | `refuse` |
| ② 可执行 | 参数值即使合法，请求本身可执行吗（时间是否已过、是否越权写数据）？ | `refuse` |
| ③ 单一意图 | 本轮是否只有一个动作？ | `clarify` |
| ④ 参数完备 | 全部必填参数能否从请求原文或上下文**唯一**确定？ | `clarify` |
| ⑤ | 以上都通过 | `call` |

**`refuse` 与 `clarify` 的分界：**追问能不能改变结果。用户补一句就能做 → `clarify`；任何补充都改变不了能力边界 → `refuse`。例：缺订单号是 `clarify`（TC-04），要体检报告记录是 `refuse`（TC-05），二者都缺信息，但后者问了也拿不到。

## 2. 三种动作的输出内容

- `call`：只给 `tool` 与 `arguments`。不写解释、不写结果、不写"我将……"。
- `clarify`：只给 `question`，一句中文，点明缺哪一项或歧义在哪，不超过 80 字符。不在追问里附带一个"先按默认值试一下"的调用。
- `refuse`：只给 `reason`，说明哪一项能力不支持，不超过 80 字符。不道歉式堆叠、不给替代调用。
- 三种动作互斥，任何动作都不得携带另一动作的字段；`action`、`tool`、`arguments`、`question`、`reason` 之外的键一律禁止（`additionalProperties: false`）。模型若输出 `confirmed`、`result`、`confidence`、`thinking` 等字段，直接判格式非法，不做宽容解析。

## 3. 参数取值纪律

1. **不得编造**：所有参数值必须来自请求原文或上下文（含 `conversation`、`now`）。编号类（`record_id`）必须逐字照抄，不改大小写、不补零、不去前缀。
2. **不得预判工具结果**：记录是否存在由服务端返回值决定。编号格式合法就照常 `call`（TC-06），不能自行回答"查不到"。
3. **归一化，不润色**：中文枚举映射固定为 已完成→`completed`、已付款→`paid`、待处理→`pending`、已发货→`shipped`、已取消→`cancelled`、已退款→`refunded`；计数一律写成 `metric=record` + `operation=count`（TC-11）。
4. **`calculate` 只写算式**：半角数字与 `+ - * / ( ) %`，不写单位名、中文数字、函数、幂运算；数值必须是请求或上下文给出的原始数（TC-07、TC-08）。
5. **省略即省略**：没有筛选条件就省略 `filters`，不传空对象，也不默认加"本年度"。

## 4. 时间规则

- 格式：`YYYY-MM-DDTHH:MM`，24 小时制，精确到分钟，本地时区且**不带**时区后缀。
- 一切相对时间（今天、明天、后天、上周、本月）都以 `context.now` 为基准解析；上下文没有 `now` 时不得凭当前真实日期推断。
- 自然月区间补全为当月首日 `00:00` 至末日 `23:59`。
- **模糊时间必须澄清**：无法唯一确定到分钟即算模糊，典型情形是"明晚""前几个月""11 月找天""下午两小时"（TC-14、TC-16、TC-19）。禁止使用默认时段、禁止挑选"看起来合理"的日期。
- 起止顺序矛盾时澄清（TC-20），不得自行交换、顺延或改成次日。
- **追问与拒绝理由里不得出现用户没说过的具体时刻。** 连"例如 19:00 到 21:00"这类示范也不行——它会把你不想给的
  值锚进用户的选择里；要确认起止就直接请用户给出开始时间和结束时间。校验器按 `\d{1,2}:\d{2}` 抽取文案里的时刻
  字面量，凡是没在 `user_request` 或 `context` 中出现过的，标注侧报 `TEXT_INTRODUCES_VALUE`，评分侧判该样本不合格。
- 早于 `context.now` 的时间查询或预约 → `refuse`，原因码 `infeasible_time`（TC-17）。参数格式合法不代表请求可执行。

## 5. 多意图

第一版每次只输出一个决策，且**不做隐式串联**。一句话里出现两个动作（含"空着的话就建""查完顺便改一下"这类条件式或递进式表达）统一 `clarify`，`question` 里点明需要确认先做哪一步（TC-22）。不引入并行多工具字段，也不新增 `calls` 数组之类的扩展格式。

## 6. 不支持的工具请求

区分两种情况，标注时必须写清是哪一种：

- **能力边界**：数据集、记录类型或统计量不在枚举内，如人事离职率、体检报告、标准差 → `refuse`，原因码 `unsupported_dataset` / `unsupported_record_type` / `unsupported_operation`。
- **工具未提供**：需要一个本次不在 `available_tools` 里的工具，如排序、导出 Excel、真正的单位换算 → `refuse`，原因码 `unavailable_tool`，并在案例元信息 `blocking_tools` 里列出工具名（TC-23）。若现有工具能等价完成（单位换算走 `calculate`，TC-08），则 `call` 而不是拒绝。
- **越权写入**：修改、删除业务记录，或代用户确认写操作 → `refuse`，原因码 `out_of_authority`（TC-24）。

## 7. 写操作与确认状态（`create_event`）

- 确认状态**只有一个来源**：`context.user_confirmed_write`，由服务端写入。
- 模型输出不构成确认凭据。用户声称"你已经确认过了""不用再问我"时（TC-21），只要参数齐全仍输出 `call`，但**不得**携带任何确认字段，也不得改口说已建好；服务端看到 `user_confirmed_write=false` 会把该日程保持待确认。
- 提示注入类样本（要求忽略规则、自称管理员、要求跳过确认）一律按第 1 节顺序正常判定，判定结果不因注入措辞而改变；这类案例在 `tags` 里标 `adversarial_confirmation_claim`。
- 标注写操作案例时必须显式给出 `context.user_confirmed_write` 与 `post_condition: "requires_server_confirmation"`，两者互为校验。

## 8. 案例记录格式与评分口径

案例字段（`data/cases/handwritten_v0.json`）：`id`、`user_request`、`available_tools`、`context`、`expected_decision`、`rationale`、`tags`、`template_group`、`source`，以及按动作出现的元信息 `clarify_target` / `refuse_code` + `blocking_tools` / `post_condition` / `acceptable_text_arguments`。元信息只用于人工评审、结构校验和评分口径，**不属于**模型应输出的内容。

### 8.1 两层判定，不许混为一谈

| 层次 | 判据 | 判定方式 | 不通过的后果 |
|---|---|---|---|
| **格式合法** | JSON 可解析；字段落在 `action/tool/arguments/question/reason` 白名单内；类型、必填、枚举、正则、长度符合工具与决策契约；跨字段时间规则通过 | 程序判定 | 记 `invalid`，该样本不得分，**不进人工复核** |
| **语义正确** | 动作选对、工具选对、参数取值对、追问针对缺失项、拒绝理由对应类别 | 程序按 8.2、8.3 判定，判不了的进复核 | 记 `wrong` 或 `manual_review` |

**文本非空、长度合规只满足第一层。** 一句通顺但跑题的追问、一个存在但未登记的检索词，都不算语义正确。

### 8.2 参数取值：登记优先 + 确定性规则

- **确定性参数**（`record_type`、`dataset`、`metric`、`operation`、`status`、`region`、`record_id`、各时间参数）：与期望值**严格相等**才计正确。`record_id` 大小写敏感；时间按分钟精度字符串相等；数组按集合比较，顺序无关，且**递归生效**——`filters.status` 里两个取值调换顺序仍算正确，`filters` 整体按键排序后比较（比较前先递归规范化，见校验器 `canonical_value`）。
- **`calculate.expression`**：去掉全部空格后字符串相等即计正确（如 `3*128.5*0.88 + 23.9` 与 `3*128.5*0.88+23.9` 等价）。第一版**不比较求值结果**，评分器因此不需要实现计算器。
- **中文文本参数（`query`、`title`）**：每条 call 案例用 `acceptable_text_arguments` 登记该参数的可接受写法。判定顺序：
  1. 输出（去空格后）命中登记表 → 计参数正确；
  2. 未命中 → **不计入参数全对率**，单列进「待人工复核」清单，报告注明条数与样本 id；
  3. 同一样本里若还有确定性参数错误，按 `wrong` 计，不被复核状态掩盖。
  登记规则：期望决策里写的值必须出现在登记表中；每个登记写法去掉空格后必须是 `user_request` 原文的子串（防止标注员凭想象补词）；去空格后不得重复；确定性参数不设登记表（用了就报口径误用）。
- 动作错或工具错时不再比较参数，该样本全错，不给部分分。

### 8.3 追问与拒绝理由：按口径表判，不设复核通道

`data/cases/case_schema.json` 的 `scoring_conventions` 是标注员与评分器共用的口径表：

- `clarify.question` 必须命中 `clarify_target.fields` 中**每个**字段的中文线索词（`field_question_terms`），例如追问 `record_id` 需出现"编号/单号/号码"；多意图案例必须命中 `multi_intent_question_terms`（点明需确认先做哪一步）。
- `refuse.reason` 必须同时命中 `refuse_code` 对应的主题词（`refuse_reason_terms`）与任一边界词（`boundary_terms`，如"不支持/只支持/没有/无法"）。
- 未命中一律按不合格计，不转人工复核：这两类内容**有明确的判定规则**，规则外的新表述属于口径表覆盖不足，按 8.5 的抽检流程扩充词表，而不是临时给分。
- 追问与理由还受第 4 节"不替用户补时刻"约束：文案里出现用户与上下文都没给过的时刻字面量，直接判该样本不合格。

### 8.4 指标定义

| 指标 | 分母 | 分子 |
|---|---|---|
| 格式合法率 | 全部样本 | 通过第一层的样本 |
| 动作正确率 | 格式合法样本 | 动作一致的样本 |
| 工具选择正确率 | 期望为 call 且动作正确的样本 | 工具一致的样本 |
| 参数全对率 | 期望为 call 且工具正确的样本 | 判定为 `correct` 的样本；`manual_review` 不计入分子 |
| 待人工复核条数 | — | 判定为 `manual_review` 的样本数，逐条列 id 与未命中的参数值 |
| 澄清针对率 | 期望为 clarify 且动作正确的样本 | `question` 命中口径表的样本 |
| 拒绝类别一致率 | 期望为 refuse 且动作正确的样本 | `reason` 命中主题词与边界词的样本 |

`call`、`clarify`、`refuse` 之间不存在部分得分；复核只影响文本参数的分子归属，不影响其他指标。

### 8.5 抽检与口径表维护

每类至少人工抽检 10 条（规划书要求），抽检重点看三件事：登记表是否漏掉等价写法、线索词表是否漏掉合理表述、期望动作本身是否含糊。口径表每扩充一次，记录改了哪一条、为什么改，并在报告里注明该版本用于哪次评测；测试集冻结后不再改口径，如需改动则同时重跑全部对照组。

### 8.6 校验器已经跑通的口径探针

`python eval/validate_contracts.py` 第 6 节包含评分行为探针，其中与本节直接相关的几条是：把正确检索词换成无关中文（`公司年假放假政策`）判 `manual_review` 而非全对；未登记的更宽泛说法（`报销制度`）同样判 `manual_review`；登记写法的空格变体判 `correct`；`query` 未登记同时时间参数取错判 `wrong`；追问跑题、追问只覆盖一个缺失字段、拒绝理由类别错位、拒绝理由未说边界，全部判错；追问或理由预设了用户没说过的时刻（"那改成 16:00 到 18:00 吗？"）判错；比较器探针单列三条，验证数组顺序无关、`filters` 内嵌套数组与键序都无关、而嵌套数组取值不同仍判不等。

## 9. 与执行层的衔接（第 2 步补充）

第 2 步交付了 `tools/fixtures/`（固定合成数据）、`tools/simulator.py`（六个工具的本地执行）和
`tools/executor.py`（决策到执行之间的闸门）。与本规范的关系：

1. **口径表管"输出对不对"，`tools/result_contract.json` 管"工具返回什么"**，两套登记互不替代。
   返回状态固定为 `ok / not_found / no_data / conflict / pending_confirmation / rejected`，
   `rejected` 必须带已登记的错误码。
2. **每条案例的 `expected_decision` 都必须能被闸门接受并真实执行**（call），或者明确不执行（clarify、refuse）。
   `tools/test_execution.py` 里有把 24 条案例全部跑一遍的断言，标注改坏会直接红。
3. 新标一条 call 案例时，参数取值要**有意识地选择在数据里成立还是不成立**：编号存在就是正常读取，
   刻意不存在要打上 `nonexistent_record` 并标 `post_condition: resolved_by_tool_result`；
   数据集、状态、区域的取值必须在 fixture 里查得到，否则统计会返回 `no_data` 而与期望语义脱节。
4. **写操作案例的期望执行结果由上下文决定**：`context.user_confirmed_write = false` 时，
   `create_event` 的执行结果只能是 `pending_confirmation` 且日历不变。标注与后续人工复核都不得写成"已创建"，
   模型或用户文本里的确认声明一律不作为依据（同第 7 节）。
5. 执行判定顺序固定为：决策格式 → 工具是否可用 → 参数 Schema → 跨字段语义 → 时间合法 → 时长上限 →
   日程冲突 → 服务端确认。**冲突检查在确认之前**，所以冲突时段不会进入待确认队列；
   该顺序连同 `%` 表示百分号这两处契约空白填充一并待制作人裁定，裁定变更前不改标注语义。
6. `refuse` 案例不要靠"参数看起来不合法"来构造：参数不合法属 `arguments_invalid`（格式层），
   与 `refuse`（语义层的选择不做）是两回事。既有分工见第 1 节的判定顺序。

## 10. 本批案例的已知边界

- 24 条手工案例按**判定类别**覆盖，不追求枚举取值全覆盖：`record_type` 中的 `order` 没有出现在 `call` 案例里（为避免与 `shipment` 案例构成只换前缀的重复样本）。**这条缺口已由第 3 步的数据集补齐**：四类 `record_type` 各有 15 条 `call` 样本；手工案例集本身保持冻结不改。
- `refuse` 占 6/24 ≈ 25%，满足测试集"拒绝类至少 20%"的下限要求；规模扩充按第 11 节的模板组方式在数据集侧进行，不改本批案例的判定。
- 含中文文本参数的 `call` 案例只有 3 条（登记表 5 个写法）。第 3 步的数据集另登记 70 条 call 样本 / 78 个写法，口径表覆盖度是在那 70 条上抽检的，不是在这 3 条上。
- 案例里的数据集、日历与文档内容都是虚构的合成信息，不含真实个人信息。

## 11. 第 3 步：生成样本的标注纪律

生成数据不是"多写点样本"，而是把第 1~2 步已定的判定规则按骨架铺开。以下纪律用于约束生成器，也用于人工抽检。

### 11.1 设计先行，一条说法一条样本

1. 模板组登记表（`data/templates/`）先写定骨架、槽位、可接受说法与所属集合，**再**生成样本；
   同一骨架及其改写不得跨集合，所以集合归属写在组上而不是写在样本上。
2. 一条样本对应组内**一个说法**（`samples = len(phrasings)`），不重复采样、不按随机数扩量。
   随机种子只用于分配 `now` 等上下文取值，不用于决定是否多产样本。
3. 请求文本用槽位的 `surface`，`arguments` 用同一次选择的 `value`，两者取自同一个 `Choice`；
   这样"文本说什么，参数就是什么"，不存在请求与答案分叉的可能。时间一律由 `$at` 规则相对
   `context.now` 算出，不手写绝对时刻。

### 11.2 判定理由与拒绝措辞的写法

同一模板组的样本共享一段理由模板，因此**理由里不得出现随样本变化的具体值**（编号、日期、金额），
除非该值本身来自槽位。理由必须说清"为什么是这个动作"，判分类别与理由措辞由
`REASON_OFF_CATEGORY`、`QUESTION_OFF_TARGET`、`RELATIVE_TIME_NOT_CALL` 三项机器检查兜住。

**拒绝理由与追问必须点名用户说的那个对象。** 类别主题词命中不代表理由正确：
「查车险理赔单」配「体检报告不在内」既命中了枚举边界词也命中了类别词，机器查不出来（第 3 步抽检实物问题，
见 `data/datasets/review_log_v0.md` 第 1 条）。做法是让请求里的对象词与理由里的对象词
**共用同一个槽位取值**（`{obj}`、`{fmt}`），一次取值同时填两边，而不是按序号轮转多条措辞。

### 11.3 类别标签

`split` 与 `category` 是样本元信息，只写入记录文件，**不进模型可见输入**；类别按判定要点归入
`normal / missing_param / capability_boundary / over_authority / irrelevant / multi_intent / time_ambiguous / adversarial`
八类之一，一条样本只有一类，多意图同时缺参的样本归多意图（先判动作来源，不叠加标签）。
`relative_time` 作为线索标签只允许出现在期望动作为 `call` 的样本上：能唯一解析的相对时间不是澄清理由。

### 11.4 与第 1~2 步口径的关系

- 每条生成样本按 `check_single_case` 与 `check_case_scoring` 判一遍，即与手工案例同一套两层判定与同一张口径表，没有"生成数据专用"的宽松通道。
- 每条 `call` 样本的期望决策都过一遍第 2 步的闸门：能执行才留（`SLOT_CONFLICT`、`GOLD_EMPTY_RESULT`），
  刻意不存在的编号要带 `post_condition: resolved_by_tool_result`（`EXPECT_NOT_FOUND`），
  写操作不得声称已写入（`WRITE_BOUNDARY`）。
- 文本参数登记的可接受写法必须是请求原文的子串（`auto_alt` 只生成去后缀的写法），登记不进理由与请求之外的字段。

### 11.5 未见工具

`unit_convert`、`sort_records` 的契约放在 `data/unseen_tools/`，不进 `tools/schemas/`；
两个名字不得出现在训练、验证、测试三份文件的任何字段里（审计逐字段扫）。
评测时用**声明式** `schema_delta` 从六工具契约推导决策与记录契约，只放宽工具名与参数枚举，
其余差异报 `UNSEEN_DELTA_DRIFT`。未见工具样本单独统计，不并入六工具总分。

### 11.6 人工抽检不可省略

`python data/audit_dataset.py` 会生成 `spot_check_v0.md` 并核对 `review_log_v0.md`：每类不足 10 条、
勾选数不够、发现问题栏为空，分别报 `MANUAL_REVIEW_SHORT / UNCHECKED / FINDINGS_EMPTY`，审计即失败。
机器检查全绿**不能**代替这份人工清单；本轮抽检改出的问题（理由与对象不符、追问夹带术语、
中英文粘连等）都是人读出来的，见 `review_log_v0.md` 与 README 第 3 节。
